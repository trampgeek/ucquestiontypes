# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is the **object-oriented (OO) variant** of RoboTurtle, a Reeborg-inspired Moodle CodeRunner question type. Students write Python to control one or more **named `RoboTurtle` objects** navigating a grid world (`alice = RoboTurtle("Alice")`, `alice.move()`), so several robots can share a world and the same class is seen to have different state per instance. It runs Python in-browser using [Skulpt](https://skulpt.org/) and grades submissions on the Jobe server.

The original single-robot question type (students call global functions such as `move()`) is the sibling folder `../python3_roboturtle/`. The two are **deliberately independent folders** (one folder per question type, so the code for a type is found by looking for the folder of the same name) with **incompatible test-case formats and student APIs**: use the matching prototype, question type and editor for each. Never put OO test cases in a question using the original type or vice versa (the usual symptom is a confusing `KeyError: 'path'`).

A few files must stay **identical** in both folders: `build.py`, `turtle.py`, `classes/item.py`, `classes/item_types.py`, `roboturtle.js`, `prototypeextra.html.template`. After changing one, copy it to the sibling. `python build.py` ends with a warning if any have drifted; `python build.py --check-sync [-v]` does only that check. Everything else (world.py, goal worlds, worldloader, the student-facing classes, help.html, the editor) differs by design.

## Build System

**Never edit `prototypeextra.html`, `template.py`, `assembledrobot.py`, `editor.html` or `questiontext.html` directly** - they are generated files. (`questiontext.html` is generated by `questions/make_questiontext.py`, the other four by `build.py`.)

All Python logic lives in `classes/`. After changing anything there, rebuild (from this folder - paths are relative):

```bash
python build.py
```

This processes four `.template` files using `{INCLUDE:path}` directives:
1. `assembledrobot.py.template` -> `assembledrobot.py` (all classes concatenated)
2. `template.py.template` -> `template.py` (Jobe server grader, includes assembledrobot + turtle stubs)
3. `prototypeextra.html.template` -> `prototypeextra.html` (browser HTML, includes assembledrobot via Skulpt and `roboturtle.js`)
4. `editor.html.template` -> `editor.html` (standalone visual test-case builder; see "World editor" below)

Lines marked `#omitfrombuild` are stripped during the build - they are used for VS Code type checking (e.g. `from turtle import Turtle`) and must not appear in the assembled output. `build.py` also substitutes `{ITEM_EMOJI_JS}` and `{ITEM_TYPE_OPTIONS_HTML}` (both derived from `classes/item_types.py`) into the editor.

## Architecture

The same Python code runs in two environments:

| Environment | File | How Python runs |
|-------------|------|----------------|
| Browser (student UI) | `prototypeextra.html` | Skulpt (Python-in-browser) |
| Jobe server (grading) | `template.py` | CPython |

`turtle.py` in the repo root is a stub that satisfies `from turtle import Turtle, Screen` on the Jobe server without doing any graphics.

### Class Hierarchy

- **`Item`** (`classes/item.py`) - collectible object; type names and emoji come from `ITEM_TYPES` in `classes/item_types.py` (dependency-free so `build.py` can load it directly).
- **`TurtleSprite`** (`classes/turtlesprite.py`) - the on-screen `turtle.Turtle` subclass with an item inventory. One per robot. Not student-facing.
- **`RoboTurtle`** (`classes/roboturtle.py`) - the **student-facing class**. `RoboTurtle(name)` *claims* the robot of that name: the world has already drawn every robot's sprite at load time (so students see the initial state before writing any code), and the constructor takes over the matching spec (`World.claim_robot_spec`). It holds the robot's grid position (`cell`), heading, `path` and colour, and implements every command and query as a method (`move()`, `turn_left/right()`, `take/put/toss()` which return the item's type name, `build_wall()`, `inventory()`, `position()`, `facing()`, `send_text()`, `speed()` ...). `move()` also refuses to enter another robot's cell. `send_text()` prefixes the robot's name and `": "`.
- **`World`** (`classes/world.py`) - base class; manages grid, wall segments, items, rendering, and the **robots**: `robot_specs` (start specs from the world JSON: name, position, heading, colour, inventory, plus `sprite` and `robot` once claimed), `robots` (the `RoboTurtle`s created so far). Subclasses auto-register via `__init_subclass__` into `World._registry`. It also owns the optional text output feature (`expected_texts`; `check_final_state()` requires `sent_texts == expected_texts`), name labels (`draw_robot_names`, drawn when there are several robots or any robot is named in the JSON), the faint `house_outline` icon (`draw_house_outline`), `set_speed()`, `redraw_world()` and `spec_for(name, index)` (resolves a per-robot goal entry to a spec). Subclasses that override `check_final_state()` must call `super().check_final_state()` first - the base also fails if any robot was never created. `on_world_loaded()` is a no-op hook called once by the loader after everything is placed.
  - **`TargetWorld`** - goal: each robot with a target reaches it. `world_params.targets` is a list; each entry is `{"robot": name, "location": [x, y]}` or a plain cell matched to the robot by list position. `target` is shorthand for robot 0. `target_icon`, `target_labels` (set false to hide the "->name" labels). `target_required = True`; subclasses may relax it.
  - **`PickUpItemsWorld`** - extends `TargetWorld` with `target_required = False`: goal is that all items end in the `item_dumps` (auto-counted from items in the world *and robots' starting inventories* when `count` is omitted) and no items remain elsewhere, plus any targets. The old singular `item_dump` is still accepted.
  - **`PathWorld`** - goal: each robot with a required path follows it exactly. `world_params.paths` is a list of `{"robot": name, "path": segments}` entries or plain segment lists matched by position; `path` is shorthand for robot 0.
- **`worldloader.py`** - `load_world(data)` builds the world via `World.create()`, records the robot start specs (`"robots"` list; the legacy single `"robot_start"` is still accepted and left unnamed), puts items in the world or in a spec's `inventory` (item `"robot"` index), then **draws the sprites before the grid is drawn** and only then switches animation on (see "Skulpt pitfalls"), and sets the `_current_world` global.
- **`globalcommands.py`** - only the global `speed(n)` (sets every robot's speed; it is what the speed selector under the display calls). Everything else is a `RoboTurtle` method. The grader's namespace in `template.py.template` therefore exposes just `RoboTurtle` and `speed` - **adding a method to `RoboTurtle` needs no change there**.

### Wall Representation

Walls are stored as a `set` of unit edge segments `((x1,y1),(x2,y2))`; `is_wall_between()` does an O(1) lookup. Longer walls and the perimeter are decomposed into unit segments on insertion. `toss()` deliberately ignores walls (but not blocked cells or the grid boundary).

### JavaScript (`roboturtle.js`)

Loaded once per page via a singleton loader (`window._skulptLoader`). Skulpt scripts come from `/local/skulpt/skulpt/` (path adjusted for `localhost` dev). `___textareaId___` is replaced by CodeRunner with a unique per-question ID at render time. On "Run": Skulpt executes `prefix_code + load_world(tests[currentTest]) + student_code`. Goal checking uses a `__ROBOTURTLE_GOAL__:` marker printed to stdout and intercepted by the JS output handler.

**Setup checks.** The first thing the script does is verify the question is set up properly and, if not, show a red "This question is not set up correctly" banner (and disable the buttons) instead of failing obscurely: Twig not applied (TwigAll not ticked), no `testcases`, invalid JSON, or not a list. This works only because **no Twig delimiter (`{{`, `{%`) may ever appear inside a `<script>`** - every placeholder lives in a hidden element (`___tests`, `___disabledfunctions`, `___maxnumlines`) that the script reads. **`roboturtle.js` is included once per question, all in one page-wide scope, so it must declare NO top-level `const`/`let`/`class`/`function` names** (a second question on the same page fails with "X has already been declared", or, for function declarations, silently has its question-specific IDs overwritten): keep everything inside a function, and use `window.` properties keyed by the question's `___textareaId___` for anything shared. Always test a change to it with TWO questions on one page. Do not write the delimiters out literally in `roboturtle.js`, even in comments or strings (the code builds them with `'{' + '{'`). `disabledfunctions` is read from its hidden element for compatibility with the original type but is **not supported** here.

### Skulpt pitfalls (learned the hard way)

- **One Skulpt run at a time, per PAGE.** All RoboTurtle questions on a page share one Skulpt and one turtle screen, so their programs must never overlap. `runSkulptWhenFree()` therefore holds `window._skActive` until the promise returned by `runSkulpt()` has settled (not merely until `runSkulpt()` returns - it only starts the run, which continues asynchronously, yielding every ~200 ms). Releasing it early used to work only because a display run normally finishes inside one slice; with the CPU throttled 20x two questions' drawings were mixed together and the second never rendered. Test with CPU throttling (Playwright: CDP `Emulation.setCPUThrottlingRate`) and two questions on one page.

- Create turtles **before** drawing the grid (`tracer(0)`), change speeds with `tracer(0)`, then `update()` and `tracer(1)`. Creating the second sprite after animation was switched on made it vanish intermittently.
- Moodle: the question must use the OO question type and have **TwigAll ticked**.

## Deployment

After building: copy `prototypeextra.html` into the OO CodeRunner prototype's **prototypeextra** field and `template.py` into its **template** field (UI plugin: html, `html_src` = prototypeextra); copy `skulpt/` to `moodle/public/local/skulpt/`; upload `turtle.py` as a support file. In each question: tick TwigAll and set the Template parameters to `{"testcases": [ ... ]}`. There is deliberately no prototype XML export in the repository (it was too much to keep in step with the source); the prototype is built by hand from the generated files. `questiontext.html` is the authoring documentation for the prototype's question text.

## World JSON Format

See `questiontext.html` (generated; includes two worked examples) or `questions/*/testcases.json`. In short:

```json
{"world_class": "TargetWorld",
 "world_params": {"targets": [{"robot": "Alice", "location": [6, 0]}, {"robot": "Bob", "location": [0, 0]}],
                  "target_icon": "house_outline", "target_labels": false},
 "grid_size": [7, 2],
 "robots": [{"name": "Alice", "position": [0, 0], "heading": "east", "colour": "blue"},
            {"name": "Bob", "position": [6, 0], "heading": "west", "colour": "red"}],
 "walls": [], "blocked_cells": [[[0, 1], [2, 1]], [[4, 1], [6, 1]]],
 "items": [{"type": "star", "position": "inventory", "count": 3, "robot": 0}]}
```

The `testcases` template parameter is `{"testcases": [ test, test, ... ]}`.

## World editor

`editor.html` (built from `editor.html.template` - edit the template) is the visual builder for this variant: a Robots panel (name, colour, start, heading, target per robot; the selected robot is what the Robot/Target/Path tools and inventory buttons act on), world-class-specific options, text output, item dumps, import/export of the complete `{"testcases": ...}` JSON, and warnings for likely mistakes. It always names robots and always exports the `robots`/`targets`/`paths` format; legacy `robot_start` tests import with the default name "Alice". The original editor in `../python3_roboturtle/` produces the other format and must not be used here.

## Extending

- **New item type:** edit `classes/item_types.py`, then `python build.py` (this also updates the editor's pickers) - and copy `item_types.py` to the sibling folder.
- **New world type:** new file in `classes/`, subclass `World` (or a subclass), override `check_final_state()` (calling `super()` first) to append to `self.fail_messages`, add `{INCLUDE:classes/yourworld.py}` to `assembledrobot.py.template`. Look robots up with `self.spec_for(name, index)` and `spec["robot"]` (the `RoboTurtle`, or `None` if never created).
- **New robot command:** a method on `RoboTurtle` in `classes/roboturtle.py`, plus a line in `help.html` and the authoring notes in `questions/make_questiontext.py`.

## Testing

There is no Moodle-free end-to-end test, but most of the stack can be checked locally (run `python build.py` first):

1. `python questions/validate.py questions/swap` - runs the model answer (`answer.py`) through the CPython grader (`template.py`), one result per test.
2. `node questions/check_skulpt.js swap` - runs the same program the browser builds under the **real Skulpt** engine (in Node, with the dummy `turtle.py`); catches Skulpt-specific incompatibilities. Run it after any change to `classes/`.
3. `questions/generate.py` rebuilds the `testcases.json` files (and `params_expanded.json`, the same data fully expanded); `questions/make_questiontext.py` rebuilds `questiontext.html` from them.
4. For the page and the editor, Playwright works well (the venv at `~/python_venv` has it). Headless Chrome can render `prototypeextra.html` if you supply stand-ins for Moodle's `M` and `require`, serve Skulpt under `/moodle5/local/skulpt/skulpt/` on `localhost`, and render the Twig placeholders yourself (a Twig library is in `~/crbackup/vendor/twig/twig`).

Not yet checked: Firefox/Safari, slow machines, and the live redraw after `build_wall()` with several robots (the command is not exposed in the student help).
